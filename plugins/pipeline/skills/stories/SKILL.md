# 기능 명세와 완료 조건 (기획 4단계)

기획서는 "어떤 서비스인지"를 말하고, 이 문서는 **"무엇이 되면 다 만든 건지"**를 말한다. 화면 만들기(`design-screen`), 서버 만들기, 코드 리뷰(`/code-review`의 Spec 기준)가 모두 이 완료 조건으로 확인한다. 결과는 `projects/<프로젝트>/stories.md`다.

## 묻는 법

[`../../references/asking.md`](../../references/asking.md)를 따른다. 이 스킬에서 특히:

- "사용자 스토리", "인수 조건", "Given/When/Then" 같은 말을 쓰지 않는다. "기능 설명 한 줄", "완료 조건(이게 되면 다 만든 것)"이라고 말한다
- 완료 조건은 Claude가 기획서에서 초안을 만들고, 사용자는 **맞는지, 빠진 게 없는지만** 본다. 사용자가 처음부터 쓰게 하지 않는다
- 완료 조건 하나는 **화면에서 눌러보고 눈으로 확인할 수 있는 것**이어야 한다. "빠르게 동작한다", "편하다"처럼 확인할 수 없는 말은 쓰지 않는다

## 진행

### 0. 준비

1. 프로젝트 `spec.md`를 읽는다. `범위`가 비어 있으면 먼저 `/pipeline:scope`를 하자고 안내한다 (범위 없이 하면 다음 학기 기능까지 명세하게 된다)
2. `stories.md`가 이미 있으면 새로 생긴 기능만 추가하거나, 바뀐 기획에 맞춰 고친다

### 1. 기능 나누기

1. `범위`의 '꼭 필요', '있으면 좋음' 기능을 가져와 `F-01`부터 번호를 붙인다
2. 기능 하나가 너무 크면(완료 조건이 7개를 넘으면) 나누자고 제안한다. 반대로 너무 작은 것(버튼 하나)은 비슷한 기능과 합친다
3. [`references/stories-template.md`](references/stories-template.md)의 '한눈에 보기' 표를 채워 보여주고 확인받는다

### 2. 기능마다 쓰기

기능 하나씩, 이 순서로 진행한다. 진행 위치를 보여준다: `[기능 명세] F-03/8 현장 대여`

1. **기능 설명 한 줄**: "<역할>로서 <하고 싶은 일>을 하고 싶다. 그래야 <얻는 것>." '얻는 것'은 기획서 `배경`의 불편과 이어지게 쓴다
2. **완료 조건 초안**: 기획서의 화면 상세(할 수 있는 것 / 비어 있을 때 / 안 될 때)와 규칙에서 뽑는다. 기능마다 이렇게 섞는다
   - 잘 되는 경우 1~2개
   - 비어 있을 때 1개
   - 안 될 때(규칙에 걸릴 때) 1~3개
3. 초안을 표로 보여주고 묻는다: "이 중에 틀린 게 있거나, 빠진 경우가 있나요?" 사용자가 떠올리기 어려우면 장면을 하나 꺼내준다
   > 근로학생이 대여 처리를 하는 사이에 학생이 앱에서 예약을 취소하면 어떻게 될까요?
4. 기획서에 없던 규칙이 새로 나오면 `spec.md`의 `규칙`에도 반영하자고 제안하고, 확인받고 고친다
5. **확인 방법**: 화면에서 눌러볼 순서를 한두 줄 쓴다. 화면 단계에서 이 순서대로 눌러본다

기능 3~4개마다 지금까지 쓴 기능 목록과 남은 개수를 보여준다.

### 3. 정리

1. `stories.md`를 저장하고 `spec.md`의 진행 상황 `기능 명세와 완료 조건`에 체크한다
2. GitHub 이슈로 올릴지 묻는다. 이슈는 개발자들이 작업을 나눠 가져가는 단위다
   - 올리기로 하면, 기능마다 이슈 하나씩 **프론트 레포**(`../konkuk-icteam-fe`)에 만든다. 서버 작업도 같은 이슈에서 함께 본다
   - 형식은 프론트 레포의 `.github/ISSUE_TEMPLATE/`과 `docs/git-conventions.md`를 따른다. 제목 `Feat(<앱>): <기능 이름>`, 라벨 `feat`, 본문 배경 = 기능 설명, 작업 내용 = 관련 화면, 완료 조건 = 표 그대로, 참고 = `stories.md`·`spec.md` 링크
   - **만들기 전에 이슈 목록(제목과 개수)을 보여주고 확인받는다.** 이슈는 팀 전체가 보는 곳이라 한 번에 많이 만들기 전에 꼭 묻는다
   - 만든 이슈 번호를 '한눈에 보기' 표의 `이슈` 칸에 적는다
3. 다음 단계를 알려준다: `/pipeline:red-team` — 기획서와 기능 명세를 함께 놓고 빈틈을 찾는다
4. 커밋할지 묻는다. 원하면 `docs(<프로젝트>): 기능 명세 작성` 형식으로, 기획서와 같은 브랜치에 커밋한다. **PR은 만들지 않는다.** 기획 단계(①~⑤)가 끝나는 `red-team`에서 한 번에 올린다

## 하지 않는 것

- 기술 구현 방법(데이터베이스 구조, 함수 이름 등)을 쓰지 않는다
- 사용자 확인 없이 GitHub 이슈를 만들지 않는다
- 다음 학기·안 함 기능의 명세를 쓰지 않는다
