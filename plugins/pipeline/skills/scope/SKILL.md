# 범위 정하기 (기획 3단계)

한 학기는 짧고 개발자는 학생이다. 기획서에 적힌 기능을 **이번 학기에 끝까지 만들 수 있는 만큼만** 고르도록 돕는다. 결과는 `spec.md`의 `범위` 섹션과 `이번에 하지 않는 것`이다.

## 묻는 법

[`../../references/asking.md`](../../references/asking.md)를 따른다. 이 스킬에서 특히:

- "우선순위", "MVP", "백로그" 같은 말을 쓰지 않는다. "이번 학기에 꼭 만들 것", "첫 버전"이라고 말한다
- 기능을 빼자고 할 때는 **빼도 서비스가 돌아가는 장면**을 같이 보여준다. 기능을 빼는 게 실패가 아니라는 걸 말해준다
  > 연체 문자 알림을 빼도, 관리자가 연체 현황 화면을 보고 직접 연락하면 돼요. 지금 엑셀로 하던 것보다는 훨씬 빨라요

## 네 가지 구분

| 구분        | 뜻                                               | 판단 질문                                                 |
| ----------- | ------------------------------------------------ | --------------------------------------------------------- |
| 꼭 필요     | 없으면 이 서비스를 쓸 이유가 없다                | "이게 없어도 지금 엑셀 대신 이 서비스를 쓸까요?" → 아니요 |
| 있으면 좋음 | 있으면 편하지만, 없어도 다른 방법으로 할 수 있다 | "없으면 어떻게 대신하나요?" → 대신할 방법이 있다          |
| 다음 학기   | 필요하지만 이번 학기에는 시간이 없다             |                                                           |
| 안 함       | 만들지 않기로 했다 (이유를 남긴다)               |                                                           |

꼭 필요한 기능부터 만들고, 시간이 남으면 '있으면 좋음'을 만든다.

## 진행

### 0. 준비

1. 프로젝트 `spec.md`를 읽는다. 시나리오와 화면 목록이 비어 있으면 먼저 `/pipeline:plan`을 하자고 안내한다
2. 이미 `범위`가 채워져 있으면 처음부터 하지 말고, 새로 생긴 기능만 나누거나 바꾸고 싶은 곳만 고친다

### 1. 팀 사정 (질문 약 3개)

하나씩 묻는다. 모르면 "잘 모르겠어요"로 넘어가고 흔한 값(프론트 2명, 서버 1명, 10주)을 임시로 쓴다.

1. 개발할 사람은 몇 명인가요? 화면 만드는 사람과 서버 만드는 사람을 나눠서
2. 언제까지 써볼 수 있는 상태가 되어야 하나요? (예: 학기 말 시연, 다음 학기 시작 전 오픈)
3. 시험 기간이나 축제처럼 개발을 못 하는 주가 있나요?

### 2. 기능 목록 만들기

1. 시나리오, 화면 상세, 규칙에서 **기능**을 뽑는다. 기능은 사용자가 할 수 있는 일 하나다 (예: "예약하기", "예약 취소", "현장 대여", "연체 현황 보기")
2. 기능마다 관련 화면 ID와 **크기**를 Claude가 어림한다

   | 크기 | 기준                                                                                                 |
   | ---- | ---------------------------------------------------------------------------------------------------- |
   | 작음 | 보기만 하는 화면 하나, 또는 버튼 하나로 끝나는 일                                                    |
   | 보통 | 입력하고 저장하는 화면, 규칙 검사가 몇 개 있는 일                                                    |
   | 큼   | 상태가 여러 단계로 바뀌는 일, 역할 여러 개가 얽힌 일, 로그인·엑셀·알림처럼 바깥 시스템과 연결하는 일 |

3. 각 기능에 Claude가 추천하는 구분과 한 줄 이유를 붙여 표로 보여준다

### 3. 나누기 (질문 약 2~5개)

1. 표를 보여주고 "이 표에서 구분을 바꾸고 싶은 줄이 있나요?"라고 묻는다. 한 번에 한 줄씩 이야기한다
2. 의견이 갈리는 기능은 판단 질문(위 표)을 장면으로 바꿔 묻는다
3. 확정한 내용으로 표를 다시 보여준다

### 4. 학기 안에 되는지 보기

1. 꼭 필요한 기능의 크기를 더해 팀 사정과 비교한다. 대략 **개발자 1명이 일주일에 '보통' 크기 1개**를 끝낸다고 본다 (시험 기간 제외). 이건 감이라는 걸 말해주고, 개발자에게 확인받자고 `열린 질문`에 남긴다
2. 넘치면 ⚠️로 알려주고, 줄일 방법을 두세 가지 제안해 고르게 한다
   - '꼭 필요'를 더 작게 쪼개기 (예: 현장 대여는 다음 학기, 예약 대여만 먼저)
   - 화면을 합치기
   - 자동으로 하려던 것을 사람이 하도록 바꾸기 (예: 자동 문자 → 관리자가 직접 연락)
3. 남으면 '있으면 좋음' 중 무엇을 먼저 넣을지 묻는다

### 5. 정리

1. `spec.md`의 `범위` 표를 채우고, 팀 사정(인원·기간)을 적는다
2. '다음 학기', '안 함'으로 간 기능은 `이번에 하지 않는 것`에도 이유와 함께 적는다
3. 이번 학기에 만들지 않는 화면은 `화면 목록`의 화면 이름 뒤에 `(다음 학기)`를 붙인다. 화면 상세는 지우지 않는다
4. 진행 상황의 `범위 정하기`에 체크하고 `updated`를 오늘로 바꾼다
5. 다음 단계를 알려준다: `/pipeline:stories` — 이번 학기 기능마다 "무엇이 되면 완성인지" 정한다
6. 커밋할지 묻는다. 원하면 `docs(<프로젝트>): 범위 정하기` 형식으로, 기획서와 같은 브랜치에 커밋한다. **PR은 만들지 않는다.** 기획 단계(①~⑤)가 끝나는 `red-team`에서 한 번에 올린다

## 하지 않는 것

- 정확한 일정(날짜별 계획)을 만들지 않는다. 일정은 개발자들이 정한다
- 사용자 확인 없이 기능을 빼거나 넣지 않는다
