# 기획 구체화 (1단계)

기획 담당과 대화하며 아이디어를 **화면을 바로 그릴 수 있을 만큼** 구체적인 기획서로 만든다. 결과는 기획 레포의 `projects/<프로젝트>/spec.md` 하나다.

## 대하는 법

상대는 개발·기획 전문가가 아니다. 이 단계의 품질은 질문의 질에서 나온다.

- **한 번에 질문 하나.** 답을 듣고 다음 질문을 정한다. 질문 목록을 한꺼번에 내밀지 않는다
- **고를 수 있게 묻는다.** 가능하면 선택지 2~4개와 예시를 같이 준다 (AskUserQuestion 사용). 추천이 있으면 첫 번째에 두고 이유를 한 줄 붙인다
- **코드 용어 금지.** "엔드포인트", "엔티티", "상태 관리", "CRUD" 같은 말을 쓰지 않는다. "화면", "버튼", "목록", "기록해 둘 정보"로 말한다
- **모호하면 장면으로 되묻는다.** "관리가 편했으면 좋겠어요" → "관리자가 월요일 아침에 이 화면을 열면 가장 먼저 뭘 확인하나요?"
- **빠진 경우를 대신 떠올려 준다.** 비어 있을 때, 실수로 눌렀을 때, 마감이 지났을 때, 두 사람이 동시에 할 때. 정하기 어려워하면 흔한 방식을 추천한다
- **범위를 줄이도록 돕는다.** 한 학기 안에 만들 수 있는지 감각을 준다. 욕심나는 기능은 "이번에 하지 않는 것"으로 옮기자고 제안한다
- 출근부(commute), 업무일지(worklog)처럼 팀에 이미 있는 서비스와 비슷한 부분은 그쪽을 예로 들면 이해가 빠르다

## 진행

### 0. 준비

1. 지금 폴더가 기획 레포(`konkuk-icteam-plan`, `projects/` 폴더가 있음)인지 확인한다. 아니면 옆 폴더 `../konkuk-icteam-plan`을 쓴다. 둘 다 없으면 사용자에게 어디 있는지 묻는다
2. `projects/` 아래 기존 프로젝트를 본다. 사용자가 말한 것이 기존 프로젝트의 새 기능이면 그 `spec.md`를 읽고 **이어서 고친다** (새 폴더를 만들지 않는다)
3. 새 프로젝트면 영문 kebab-case 폴더 이름을 제안하고 확인받는다 (예: `equipment-rental`)

### 1. 큰 그림

순서대로 하나씩 묻고, 답이 나올 때마다 [`references/spec-template.md`](references/spec-template.md) 모양으로 `spec.md`에 바로 적는다. 대화가 끊겨도 적은 데까지는 남게 한다.

1. **무엇이 불편한가** — 지금은 어떻게 하고 있나요? (엑셀, 카톡, 종이…) 무엇이 제일 번거롭나요? → `배경`
2. **누가 쓰나** — 역할을 나눈다 (근로학생, 관리자, 외부 학생 등). 역할마다 PC인지 모바일인지 → `사용자`
3. **한 줄 소개** — 지금까지 들은 걸로 Claude가 한 문장을 써서 맞는지 확인받는다

### 2. 시나리오

역할마다 "이 서비스를 여는 가장 흔한 이유"부터 묻는다. 한 시나리오를 **처음부터 끝까지 따라가며** 단계마다 묻는다:

- 처음 열면 무엇이 보여야 하나요?
- 그다음 무엇을 누르나요? 누르면 어디로 가나요?
- 끝나면 무엇이 바뀌나요? 누가 그걸 알게 되나요?

역할마다 2~4개 시나리오면 충분하다. 시나리오를 적으면서 등장한 화면에 `S-01`부터 ID를 붙인다.

### 3. 화면

시나리오에서 나온 화면을 `화면 목록` 표로 정리해 보여주고, 빠진 화면이나 합칠 화면이 없는지 확인한다. 그다음 화면마다 `화면 상세` 네 칸(보이는 것 / 할 수 있는 것 / 비어 있을 때 / 안 될 때)을 채운다.

- "보이는 것"은 **위에서 아래 순서로** 적게 한다. 다음 단계에서 그대로 화면이 된다
- 화면에 들어갈 요소는 팀 디자인 시스템에 있는 것으로 말해주면 좋다: 버튼, 탭, 칩(상태 표시), 달력, 드롭다운, 확인 팝업, 하단 고정 버튼 등. 목록은 `../konkuk-icteam-fe/packages/design-system/CATALOG.md`의 "상황별로 고르기" 표에 있다. 사용자에게 컴포넌트 이름을 외우게 하지는 않는다
- 화면을 그려 보여주면 이해가 빠를 때는 간단한 와이어프레임(박스와 글자)을 보여줘도 된다

### 4. 데이터와 규칙

화면에 나온 정보를 모아 `데이터` 표를 만든다. 사용자에게는 "이 서비스가 기억해야 할 것"이라고 설명한다.

- 한글 이름은 사용자 말 그대로, 영문 이름은 Claude가 제안한다 (camelCase, 출근부 API의 이름과 겹치면 같은 이름을 쓴다)
- 신청·승인처럼 단계가 있는 것은 `상태` 표로 정리한다. "누가 언제 바꾸나"를 꼭 묻는다
- 권한(누가 보고 누가 고칠 수 있나), 기한, 개수 제한은 `규칙`에 적는다

### 5. 정리

1. 이번 대화에서 정하지 못한 것은 `열린 질문`에, 범위에서 뺀 것은 `이번에 하지 않는 것`에 적는다
2. `spec.md` 전체를 다시 읽고 시나리오 ↔ 화면 목록 ↔ 화면 상세 ↔ 데이터가 서로 맞는지 확인한다 (시나리오에만 있고 화면 목록에 없는 화면, 화면에는 보이는데 데이터 표에 없는 정보 등). 어긋난 곳은 사용자에게 물어 고친다
3. frontmatter의 `updated`를 오늘 날짜로, `stage`는 `plan`으로 둔다. 진행 상황의 `기획`에 체크한다
4. 사용자에게 다음을 짧게 알려준다:
   - 기획서 위치와 한 줄 요약 (화면 몇 개, 역할 몇 개)
   - 남은 열린 질문
   - 다음 단계: 프론트 레포(`konkuk-icteam-fe`)를 열고 `/pipeline:design-screen <프로젝트>`
5. 커밋할지 물어본다. 원하면 `docs(<프로젝트>): 기획서 작성` 형식으로 커밋한다. GitHub 이슈 등록이 필요하면 프론트 레포의 `/to-spec` 흐름을 안내한다

## 하지 않는 것

- 화면 코드, API, 데이터베이스 설계를 하지 않는다. 그건 다음 단계들이 `spec.md`를 읽고 한다
- 사용자가 답하지 않은 내용을 지어내 확정하지 않는다. 추천은 하되, 사용자가 고른 것만 적는다. 추측으로 채운 칸은 `열린 질문`으로 옮긴다
