# 기획서 쓰기 (기획 1단계)

기획 담당과 대화하며 아이디어를 **화면을 바로 그릴 수 있을 만큼** 구체적인 기획서로 만든다. 결과는 기획 레포의 `projects/<프로젝트>/spec.md` 하나다.

## 묻는 법

**시작하기 전에 [`../../references/asking.md`](../../references/asking.md)를 읽고 그대로 따른다.** 요약하면:

1. 왜 묻는지 먼저 말한다
2. 선택지마다 고르면 어떻게 되는지 쓴다
3. "잘 모르겠어요"를 항상 선택지로 둔다
4. 장면으로 묻는다
5. 질문은 한 번에 하나, 진행 위치를 보여준다 (`[기획서 2/5단계 · 시나리오] 질문 3/약 6`)
6. 질문 3~4개마다 들은 걸 정리해 확인한다
7. 처음 나오는 말은 풀어 쓰고, 서비스 안에서 쓸 낱말은 뜻을 정해 확인받는다
8. 나중에 바꾸기 어려운 결정은 `⚠️`로 표시하고 한 번 더 확인한다

이 스킬에서 특히 지킬 것:

- 출근부(commute), 업무일지(worklog)처럼 팀에 이미 있는 서비스와 비슷한 부분은 그걸 예로 든다
- 빠진 경우(비어 있을 때, 실수로 눌렀을 때, 마감이 지났을 때, 두 사람이 동시에 할 때)는 사용자가 떠올리기 어렵다. Claude가 먼저 장면을 꺼내 묻는다
- 욕심나는 기능이 나오면 적어두되, 지금 정할 필요는 없다고 말한다. 이번 학기에 할지는 다음 스킬(`scope`)에서 정한다

## 진행

5단계로 나눈다. 단계를 시작할 때 "이번 단계에서는 ~를 정해요 (질문 약 N개)"라고 알려준다.

### 0. 준비

1. 지금 폴더가 기획 레포(`konkuk-icteam-plan`, `projects/` 폴더가 있음)인지 확인한다. 아니면 옆 폴더 `../konkuk-icteam-plan`을 쓴다. 둘 다 없으면 사용자에게 어디 있는지 묻는다
2. `projects/` 아래 기존 프로젝트를 본다. 사용자가 말한 것이 기존 프로젝트의 새 기능이면 그 `spec.md`를 읽고 **이어서 고친다** (새 폴더를 만들지 않는다). 기획서가 이미 중간까지 있으면 비어 있는 단계부터 이어간다
3. 새 프로젝트면 영문 kebab-case 폴더 이름을 제안하고 확인받는다 (예: `equipment-rental`). "폴더 이름은 영어로만 쓸 수 있어서 제가 정할게요"처럼 이유를 말한다
4. [`references/spec-template.md`](references/spec-template.md)로 `spec.md` 뼈대를 먼저 만든다. 답이 나올 때마다 바로 적어서, 대화가 끊겨도 적은 데까지는 남게 한다

### 1. 큰 그림 (질문 약 4개)

1. **무엇이 불편한가** — 선택지 없이 묻고 예시를 붙인다: "지금은 어떻게 하고 있나요? 예: 엑셀에 적어요 / 카톡방으로 받아요 / 종이 대장에 써요". 이어서 무엇이 가장 번거로운지 묻는다 (여러 개 고르기 가능) → `배경`
2. **⚠️ 누가 쓰나** — 역할을 나눈다 (학생, 근로학생, 관리자 등). 역할마다 하는 일을 한 줄씩 정리해 보여준다 → `사용자`
3. **역할마다 기기** — 폰인지 PC인지. "출근부처럼 근로학생은 폰, 관리자는 PC" 같은 예를 든다
4. **한 줄 소개** — 지금까지 들은 걸로 Claude가 한 문장을 써서 맞는지 확인받는다

### 2. 시나리오 (역할마다 질문 약 3~5개)

역할마다 "이 서비스를 여는 가장 흔한 이유"부터 묻는다. 한 시나리오를 **처음부터 끝까지 따라가며** 장면마다 묻는다:

- 처음 열면 무엇이 보여야 하나요?
- 그다음 무엇을 누르나요? 누르면 어디로 가나요?
- 끝나면 무엇이 바뀌나요? 누가 그걸 알게 되나요?
- 이 과정에서 무엇을 고르거나 적어야 하나요? (날짜, 개수, 메모 등)

역할마다 2~4개 시나리오면 충분하다. 시나리오를 적으면서 등장한 화면에 `S-01`부터 ID를 붙인다. 시나리오 하나가 끝날 때마다 번호 목록으로 정리해 보여주고 확인받는다.

### 3. 화면 (질문 약 2~4개)

1. 시나리오에서 나온 화면을 `화면 목록` 표로 정리해 보여주고, 빠진 화면이나 합칠 화면이 없는지 묻는다
2. 화면마다 `화면 상세` 네 칸(보이는 것 / 할 수 있는 것 / 비어 있을 때 / 안 될 때)을 **지금까지의 답으로 먼저 채운다.** 화면마다 처음부터 묻지 않는다
3. 초안을 쓰다 보면 답에 없던 것(새 기능, 숫자, 세는 법 등)을 Claude가 덧붙이게 된다. 그런 것은 따로 모아 두었다가, 초안을 보여준 직후 하나씩 확인받는다. 확인받기 전까지는 `열린 질문`에 "(Claude 제안, 확인 전)"으로 적는다

- "보이는 것"은 **위에서 아래 순서로** 적는다. 다음 단계에서 그대로 화면이 된다
- 화면에 들어갈 요소는 팀 디자인 시스템에 있는 것으로 말해주면 좋다: 버튼, 탭, 칩(상태 표시), 달력, 드롭다운, 확인 팝업, 하단 고정 버튼 등. 목록은 `../konkuk-icteam-fe/packages/design-system/CATALOG.md`의 "상황별로 고르기" 표에 있다. 사용자에게 컴포넌트 이름을 외우게 하지는 않는다
- 말로 설명하기 어려운 화면은 박스와 글자로 간단한 그림(와이어프레임)을 그려 보여주며 묻는다

### 4. 데이터와 규칙 (질문 약 3~5개)

사용자에게는 "이 서비스가 기억해 둬야 할 것"이라고 설명한다.

1. 화면에 나온 정보를 모아 `데이터` 표 초안을 만들어 보여준다. 한글 이름은 사용자가 쓴 말 그대로, 영문 이름은 Claude가 정한다 (camelCase, 출근부와 겹치면 같은 이름)
2. **⚠️ 세는 단위**를 확인한다: "노트북을 '10대'처럼 개수로만 셀까요, '노트북-03'처럼 한 대씩 번호를 붙일까요?"
3. **⚠️ 단계가 있는 것**(신청 → 승인 등)은 `상태` 표로 정리하고, 상태마다 "누가, 언제 다음 상태로 바꾸나"를 묻는다
4. 권한(누가 보고 누가 고칠 수 있나), 기한, 개수 제한을 장면으로 묻고 `규칙`에 적는다

### 5. 정리

1. 정하지 못한 것은 `열린 질문`에, 범위 밖으로 정한 것은 `이번에 하지 않는 것`에 적는다. 열린 질문마다 "누구에게 물어보면 되는지"를 함께 적는다
2. `spec.md` 전체를 다시 읽고 시나리오 ↔ 화면 목록 ↔ 화면 상세 ↔ 데이터가 서로 맞는지 가볍게 확인한다. 어긋난 곳은 사용자에게 물어 고친다 (꼼꼼한 점검은 `red-team`이 한다)
3. frontmatter의 `updated`를 오늘 날짜로, `stage`는 `plan`으로 둔다. 진행 상황의 `기획서`에 체크한다
4. 사용자에게 알려준다:
   - 기획서 위치와 한 줄 요약 (역할 몇 개, 화면 몇 개)
   - 남은 열린 질문과 각각 누구에게 물어볼지
   - 다음 단계: 열린 질문 중 현장 사람(관리자, 근로학생)이 답할 게 있으면 `/pipeline:interview`, 없으면 `/pipeline:scope`. 헷갈리면 `/pipeline:kickoff`가 알려준다
5. 커밋할지 물어본다. 원하면 `docs(<프로젝트>): 기획서 작성` 형식으로 커밋한다. 브랜치는 기획 단계 내내 하나를 쓴다 (예: `docs/<프로젝트>-plan`). **PR은 만들지 않는다.** 기획 단계(①~⑤)가 끝나는 `red-team`에서 한 번에 올린다

## 하지 않는 것

- 화면 코드, API, 데이터베이스 설계를 하지 않는다. 그건 다음 단계들이 `spec.md`를 읽고 한다
- 사용자가 답하지 않은 내용을 지어내 확정하지 않는다. 추천은 하되, 사용자가 고른 것만 적는다. "잘 모르겠어요"로 임시로 정한 것은 `열린 질문`에 `(임시: ...)`로 남긴다
- 이번 학기에 할지 말지는 정하지 않는다. 그건 `scope`의 일이다
