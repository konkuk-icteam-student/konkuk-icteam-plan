# 빈틈 점검 (기획 5단계)

개발에 들어간 뒤 빈틈이 나오면 화면과 서버를 다 고쳐야 한다. 그 전에 Claude가 **일부러 깐깐한 사람이 되어** 기획을 다시 읽는다. 결과는 고쳐진 `spec.md`·`stories.md`와 점검 기록 `projects/<프로젝트>/red-team.md`다.

## 묻는 법

[`../../references/asking.md`](../../references/asking.md)를 따른다. 이 스킬에서 특히:

- 빈틈을 찾는 건 기획을 잘못했다는 뜻이 아니라고 먼저 말한다. "개발 전에 찾으면 고치기 쉬워서, 일부러 깐깐하게 볼게요"
- 찾은 것을 한꺼번에 쏟아내지 않는다. 중요한 것부터 하나씩 정한다
- 빈틈마다 **실제로 일어나는 장면**으로 설명한다
  > 노트북이 딱 1대 남았을 때, 두 학생이 같은 시각에 예약 버튼을 누르면 둘 다 예약될 수 있어요. 한 명은 창구에 왔는데 노트북이 없겠죠

## 진행

### 1. 읽고 찾기 (사용자에게 묻지 않고 Claude가 혼자)

1. 프로젝트의 `spec.md`, `stories.md`(있으면), `interviews/`(있으면)를 모두 읽는다. `stories.md`가 없으면 기획서만으로 하되, 끝나고 `/pipeline:stories`를 하자고 안내한다
2. [`references/checklist.md`](references/checklist.md)의 A~E를 하나씩 확인하며 빈틈을 모은다. 목록에 없는 것도 이 서비스에서 문제가 될 만하면 넣는다
3. 빈틈마다 무게를 매긴다

   | 무게           | 뜻                                                        |
   | -------------- | --------------------------------------------------------- |
   | 🔴 꼭 정하기   | 안 정하면 화면이나 서버를 만들 수 없다. 개발 전에 정한다  |
   | 🟡 정하면 좋음 | 개발자가 임시로 정할 수 있지만, 나중에 바꾸면 일이 생긴다 |
   | ⚪ 참고        | 알고만 있으면 된다                                        |

### 2. 보여주기

무게별 개수와 🔴 목록을 먼저 보여준다. 🟡·⚪는 제목만.

> 빈틈 9개를 찾았어요. 🔴 꼭 정하기 3개, 🟡 정하면 좋음 4개, ⚪ 참고 2개예요.
> 🔴부터 하나씩 정해볼게요.

### 3. 하나씩 정하기

1. 🔴부터 하나씩, 장면으로 설명하고 선택지(asking.md 규칙 2, 3)로 묻는다. 진행 위치를 보여준다: `[빈틈 점검] 🔴 2/3`
2. 사용자가 고른 대로 `spec.md`(규칙, 화면 상세, 상태, 데이터)와 `stories.md`(완료 조건)를 함께 고친다. 고친 곳을 한 줄로 알려준다
3. 현장 사람만 답할 수 있으면 `열린 질문`에 남기고 `/pipeline:interview`를 제안한다
4. 🔴가 끝나면 🟡를 계속할지 묻는다. 그만두면 남은 🟡는 `열린 질문`에 `(빈틈 점검)`을 붙여 남긴다

### 4. 정리

1. `red-team.md`에 점검 날짜, 찾은 빈틈, 무게, 어떻게 정했는지(또는 남겼는지)를 표로 남긴다
2. `spec.md`의 진행 상황 `빈틈 점검`에 체크하고, 기획 하위 단계가 모두 끝났으면 `기획`에도 체크한다. `updated`를 오늘로 바꾼다
3. 남은 🔴가 있으면 개발로 넘어가지 말자고 말한다
4. 다 끝났으면 다음 단계를 알려준다: 프론트 레포(`konkuk-icteam-fe`)를 열고 `/pipeline:design-screen <프로젝트>`
5. 커밋할지 묻는다. 원하면 `docs(<프로젝트>): 기획 빈틈 점검 반영` 형식으로, 기획서와 같은 브랜치에 커밋한다
6. 기획 하위 단계가 모두 끝났으면(남은 🔴 없음) **이때 처음으로** PR을 만들지 묻는다. 기획 단계 중간에는 PR을 만들지 않는다
   - 제목은 `Docs(<프로젝트>): <서비스 이름> 기획`, 본문에는 한 줄 소개, 역할·화면·기능 수, 남은 열린 질문, 다음 단계(`/pipeline:design-screen`)를 적는다
   - 남은 🔴가 있거나 기획이 덜 끝났으면 커밋만 하고 PR은 미룬다

## 하지 않는 것

- 사용자 확인 없이 기획서를 고치지 않는다. 오타·표 정리처럼 뜻이 바뀌지 않는 것만 바로 고치고 알린다
- 기획을 새로 짜지 않는다. 빈틈을 메우는 데까지만 한다
- 기술 설계 문제(서버 구조, 성능 등)는 다루지 않는다. 동시에 누르는 경우처럼 사용자가 겪는 결과로만 말한다
