# 빈틈 점검 목록

`red-team`이 기획서(`spec.md`)와 기능 명세(`stories.md`)를 읽으며 하나씩 확인하는 목록이다. 괄호 안은 장비 대여 기획 실험에서 실제로 나온 빈틈이다.

## A. 서로 맞는지

- [ ] 시나리오에 나온 화면이 모두 `화면 목록`에 있는가
- [ ] 화면 상세에 보이는 정보가 모두 `데이터` 표에 있는가
- [ ] 화면에 보이는 상태 이름이 모두 `상태` 표에 있는가 (화면엔 '연체 반납' 칩이 있는데 상태 표엔 없었음)
- [ ] `규칙`과 `범위`가 서로 맞는가 (다음 학기로 미룬 기능이 규칙에 남아 있지 않은가)
- [ ] `stories.md`의 완료 조건이 `규칙`과 다르게 말하지 않는가
- [ ] 같은 것을 다른 낱말로 부르지 않는가 (예약 / 신청 / 대여가 섞임)
- [ ] 한 사람이 둘 이상의 역할을 가질 수 있는가, 그때 화면은 어떻게 되는가 (근로학생도 장비를 빌리는 학생일 수 있음)

## B. 숫자·날짜·시각의 경계

- [ ] 기간을 세는 법이 정해져 있는가: 시작일·끝 날을 포함하나, 주말을 세나 ("3일"의 뜻이 정해지지 않았음)
- [ ] '오늘', '마감' 같은 말의 정확한 시각이 있는가 (자동 취소가 창구 닫는 시각 기준인데 시각이 없었음)
- [ ] 주말, 공휴일, 방학에는 어떻게 되는가 (목업 반납일이 주말에 걸림)
- [ ] 개수가 0일 때, 1일 때, 최대일 때 화면이 어떻게 되는가
- [ ] 미래에 잡힌 것과 지금 하는 것이 부딪히지 않는가 (현장 대여가 내일 예약분 수량을 써버릴 수 있었음)

## C. 장면별 빈틈

- [ ] 처음 쓰는 사람: 데이터가 하나도 없을 때 화면
- [ ] 실수했을 때 되돌릴 수 있는가 (잘못 누른 반납, 잘못 고른 기기 번호)
- [ ] 두 사람이 동시에 같은 것을 할 때 (마지막 한 대를 두 명이 동시에 예약)
- [ ] 중간에 그만뒀을 때 (예약해 놓고 안 옴, 입력하다 나감)
- [ ] 지우거나 폐기한 뒤 지난 기록은 어떻게 보이는가
- [ ] 권한 없는 사람이 주소를 직접 쳐서 들어오면

## D. 개인정보

- [ ] 휴대폰 번호, 학번 같은 정보를 누가 볼 수 있는가. 꼭 필요한 사람만 보는가
- [ ] 그 정보를 언제까지 보관하는가 (졸업생, 지난 학기 기록)

## E. 출시 후 실패 가정

"한 달 뒤 아무도 이 서비스를 안 쓰고 다시 엑셀로 돌아갔다면, 왜일까?"를 역할마다 생각한다.

- [ ] 처음 쓰는 사람은 서비스가 있다는 걸 어떻게 아는가
- [ ] 지금 방식보다 손이 더 가는 순간이 있는가 (창구에서 엑셀은 한 줄인데 앱은 화면 3개를 거침)
- [ ] 이 서비스가 멈추거나 틀리면 현장에서 어떻게 버티는가
- [ ] 관리자가 이 서비스를 계속 열어볼 이유가 있는가
