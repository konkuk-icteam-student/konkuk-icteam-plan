# 사용 가이드

기획 담당이 처음 프로젝트를 시작해서 화면까지 가는 길을 순서대로 설명합니다. 개발을 몰라도 따라 할 수 있게 썼어요.

> **딱 하나만 기억하세요: `/pipeline:kickoff`**
> 어디까지 했는지, 다음에 뭘 하면 되는지 모를 때마다 이것만 치면 됩니다. 프로젝트 파일을 읽고 지금 단계를 보여준 뒤, 다음 스킬을 대신 시작해 줘요.

## 시작 전 준비

처음 한 번만 하면 됩니다.

1. **레포 받기**: 세 레포를 같은 폴더 안에 나란히 받습니다. 스킬이 서로의 위치를 이렇게 찾아요.
   ```
   icteam/
   ├── konkuk-icteam-plan/   기획 (지금 이 레포)
   ├── konkuk-icteam-fe/     프론트엔드
   └── icteam-server/        서버
   ```
   기획만 한다면 `konkuk-icteam-plan` 하나만 있어도 됩니다. 화면 단계부터 `konkuk-icteam-fe`가 필요해요.
2. **플러그인 설치**: Claude Code(데스크톱 앱 또는 터미널)에서 차례로 입력합니다.
   ```
   /plugin marketplace add konkuk-icteam-student/konkuk-icteam-plan
   /plugin install pipeline@icteam
   ```
3. **기획 레포 열기**: Claude Code에서 `konkuk-icteam-plan` 폴더를 엽니다. 기획 단계는 모두 이 폴더에서 해요.

스킬이 바뀌었다는 안내를 받으면 `/plugin marketplace update icteam`으로 최신 버전을 받으세요.

## 전체 순서

```
기획 (konkuk-icteam-plan)                                   개발 (konkuk-icteam-fe, icteam-server)
① 기획서 → ② 현장 인터뷰 → ③ 범위 → ④ 기능 명세 → ⑤ 빈틈 점검 → 화면 → API 명세 → 서버 → 연동 → 배포
   plan      interview      scope     stories       red-team    design-screen  (준비 중)
             (필요할 때)
```

| 단계 | 명령 | 한 줄로 | 걸리는 정도 |
| --- | --- | --- | --- |
| 길잡이 | `/pipeline:kickoff` | 지금 어디까지 왔는지 보고 다음 단계를 시작 | 질문 1개 |
| ① 기획서 | `/pipeline:plan` | 질문에 답하면 기획서가 만들어져요 | 질문 약 20개 |
| ② 현장 인터뷰 | `/pipeline:interview` | 관리자·근로학생에게 물어볼 질문지를 만들고, 받은 답을 반영 | 질문지 1장 |
| ③ 범위 | `/pipeline:scope` | 이번 학기에 만들 것과 미룰 것을 나눠요 | 질문 약 6개 |
| ④ 기능 명세 | `/pipeline:stories` | 기능마다 "이게 되면 완성"을 정해요 | 기능마다 확인 |
| ⑤ 빈틈 점검 | `/pipeline:red-team` | 놓친 예외 상황을 찾아 메워요 | 빈틈마다 질문 |
| 화면 | `/pipeline:design-screen` | 디자인 시스템으로 실제로 눌러볼 수 있는 화면을 만들어요 | 화면마다 확인 |

②는 기획서에 현장 사람만 답할 수 있는 질문이 남았을 때만 해요. 없으면 건너뛰어도 됩니다. 나머지는 순서대로 하는 게 좋아요. 앞 단계의 결과를 다음 단계가 읽기 때문이에요.

## 단계별 설명

### 길잡이 — `/pipeline:kickoff`

**언제**: 처음 시작할 때, 오랜만에 돌아왔을 때, 다음에 뭘 할지 모를 때.

**하는 일**: `projects/` 폴더의 파일을 읽고 지금 위치를 이렇게 보여줘요.

```
✅ ① 기획서 → 👉 ③ 범위 → ④ 기능 명세 → ⑤ 빈틈 점검 → 화면 …
(② 현장 인터뷰는 건너뛰었어요)
```

그리고 `시작하기 (추천)` / `다른 단계 하기` / `오늘은 여기까지` 중에 고르게 해요. 시작하기를 고르면 그 단계 스킬이 바로 이어서 시작됩니다. 프로젝트가 여러 개면 먼저 어느 프로젝트인지 물어요.

### ① 기획서 — `/pipeline:plan`

**언제**: 새 서비스 아이디어가 있을 때, 기존 서비스에 기능을 더하고 싶을 때.

**하는 일**: 5단계로 나눠 질문하고, 답할 때마다 바로 `spec.md`에 적어요. 중간에 끊겨도 적은 데까지는 남아요.

| 단계 | 정하는 것 | 질문 수 |
| --- | --- | --- |
| 1. 큰 그림 | 지금 무엇이 불편한지, 누가 쓰는지, 폰인지 PC인지, 한 줄 소개 | 약 4개 |
| 2. 시나리오 | 역할마다 "앱을 열어서 끝날 때까지" 무엇을 보고 누르는지 | 역할마다 3~5개 |
| 3. 화면 | 화면 목록과 화면마다 보이는 것·할 수 있는 것·비어 있을 때·안 될 때 | 약 2~4개 |
| 4. 데이터와 규칙 | 서비스가 기억해야 할 것, 상태(신청 → 승인 등), 기한·개수 제한 | 약 3~5개 |
| 5. 정리 | 정하지 못한 것(열린 질문)과 이번에 하지 않을 것 | — |

화면 상세는 Claude가 그때까지의 답으로 먼저 채우고 보여줘요. 기획 담당은 맞는지만 보면 됩니다.

**남는 것**: `projects/<프로젝트>/spec.md`

### ② 현장 인터뷰 — `/pipeline:interview` (필요할 때)

**언제**: 기획서의 `열린 질문`에 관리자 선생님이나 근로학생만 답할 수 있는 것이 있을 때. 예를 들어 "창구는 몇 시에 닫나요?" 같은 질문이요.

**하는 일**: 두 번에 나눠서 써요.

1. **인터뷰 전** (`/pipeline:interview <프로젝트> prep`): 열린 질문을 답해줄 사람별로 묶고, 그 사람에게 보낼 질문지(5~8개, 10분 분량)를 만들어요. 카톡이나 메일로 보낼 거라면 인사말까지 다듬어 줘요. **보내는 건 기획 담당이 직접** 합니다.
2. **답을 받은 뒤** (`/pipeline:interview <프로젝트> summarize`): 받은 답을 붙여 넣거나 캡처를 올리면, 질문별로 정리하고 기획서의 어디를 고칠지 하나씩 확인받아 반영해요.

**남는 것**: `projects/<프로젝트>/interviews/<날짜>-<대상>.md`, 고쳐진 `spec.md`

### ③ 범위 — `/pipeline:scope`

**언제**: 기획서가 다 쓰였을 때. "이걸 이번 학기에 다 만들 수 있을까?"를 정해요.

**하는 일**:

1. 개발할 사람이 몇 명인지, 언제까지 써볼 수 있어야 하는지, 개발 못 하는 주(시험 기간 등)가 있는지 물어요.
2. 기획서에서 기능을 뽑아 크기(작음 / 보통 / 큼)를 어림하고, 네 가지로 나눈 추천 표를 보여줘요.
   - **꼭 필요**: 없으면 이 서비스를 쓸 이유가 없는 것
   - **있으면 좋음**: 없어도 다른 방법으로 할 수 있는 것
   - **다음 학기**: 필요하지만 이번에는 시간이 없는 것
   - **안 함**: 만들지 않기로 한 것
3. 바꾸고 싶은 줄을 하나씩 정하고, 꼭 필요한 기능이 학기 안에 들어가는지 확인해요. 넘치면 줄이는 방법을 두세 가지 제안해요.

기능을 빼는 건 실패가 아니에요. 빼도 서비스가 돌아가는 장면을 같이 보여주니까 안심하고 정해도 됩니다.

**남는 것**: `spec.md`의 `범위` 표와 `이번에 하지 않는 것`

### ④ 기능 명세 — `/pipeline:stories`

**언제**: 범위를 정한 뒤. 개발자에게 "무엇이 되면 다 만든 건지" 알려주는 문서예요.

**하는 일**: 이번 학기 기능마다 `F-01`부터 번호를 붙이고, 하나씩 아래를 만들어요.

- **기능 설명 한 줄**: "학생으로서 노트북을 미리 예약하고 싶다. 그래야 창구에서 기다리지 않는다."
- **완료 조건 표**: 상황 / 이렇게 하면 / 이렇게 된다. 잘 되는 경우, 비어 있을 때, 규칙에 걸릴 때를 섞어서 써요.
- **확인 방법**: 화면에서 눌러볼 순서

초안은 Claude가 기획서에서 만들고, 기획 담당은 틀린 것과 빠진 것만 봐요. 다 쓰면 기능마다 프론트 레포에 GitHub 이슈를 만들지 물어요. 만들기 전에 목록을 먼저 보여주고 확인받아요.

**남는 것**: `projects/<프로젝트>/stories.md`, (원하면) 프론트 레포 이슈

### ⑤ 빈틈 점검 — `/pipeline:red-team`

**언제**: 기획의 마지막. 개발로 넘기기 직전에 해요.

**하는 일**: Claude가 일부러 깐깐한 사람이 되어 기획서와 기능 명세를 다시 읽어요. 아래 다섯 가지를 확인합니다.

- 문서끼리 서로 맞는지
- 날짜·숫자의 경계 (마감 당일, 0개 남았을 때 등)
- 장면마다 빠진 경우 (두 사람이 동시에 누를 때 등)
- 개인정보
- "출시했는데 아무도 안 쓴다면 왜일까"

찾은 빈틈은 무게를 붙여 보여주고, 중요한 것부터 하나씩 정해요.

| 표시 | 뜻 |
| --- | --- |
| 🔴 꼭 정하기 | 안 정하면 화면이나 서버를 만들 수 없어요. 개발 전에 정해요 |
| 🟡 정하면 좋음 | 개발자가 임시로 정할 수 있지만, 나중에 바꾸면 일이 생겨요 |
| ⚪ 참고 | 알고만 있으면 돼요 |

🔴가 남아 있으면 개발로 넘어가지 말자고 안내해요.

**남는 것**: `projects/<프로젝트>/red-team.md`, 고쳐진 `spec.md`·`stories.md`

### 화면 — `/pipeline:design-screen`

**언제**: 기획이 모두 끝난 뒤.

**어디서**: **프론트 레포**(`konkuk-icteam-fe`)를 열고 `/pipeline:design-screen <프로젝트>`를 쳐요.

**하는 일**: 기획서의 화면 목록을 팀 디자인 시스템 부품(버튼, 탭, 달력, 팝업 등)으로 조립해 실제로 눌러볼 수 있는 화면을 만들어요. 서버가 아직 없으니 그럴듯한 예시 데이터로 움직여요. 화면을 하나 만들 때마다 스크린샷을 보여주고, 기능 명세의 확인 방법대로 눌러본 뒤 "바꾸고 싶은 곳이 있나요?"라고 물어요.

마지막에는 PR(코드를 합쳐 달라는 요청)을 올려요. **프론트 레포의 머지는 개발자가 리뷰한 뒤 직접** 합니다. Claude는 머지하지 않아요.

### 그다음 (준비 중)

API 명세 → 서버 → 연동 → 배포는 개발자가 이어서 해요. 스킬은 아직 준비 중입니다.

## 대화하는 법

모든 기획 스킬은 같은 질문 규칙([`asking.md`](../plugins/pipeline/references/asking.md))을 따릅니다. 그래서 질문은 늘 이런 모양으로 와요.

```
[기획서 2/5단계 · 시나리오] 질문 3/약 6

학생이 예약한 날 창구에 안 오면 어떻게 할지 정할게요.
이걸 정해야 예약 화면에 안내 문구를 넣을 수 있어요.

  1. 그날 창구 닫을 때 자동 취소 (추천) — 다른 학생이 바로 빌릴 수 있어요
  2. 근로학생이 직접 취소 — 사정이 있는 학생을 봐줄 수 있지만, 손이 더 가요
  3. 잘 모르겠어요 — 일단 1번으로 적어두고 나중에 다시 정해요
```

- **진행 위치**: 맨 위에 지금 몇 번째 질문인지, 대략 몇 개 남았는지 보여줘요.
- **왜 묻는지**: 질문마다 이걸 정하면 무엇이 되는지 먼저 말해줘요.
- **잘 모르겠어요**: 언제든 골라도 돼요. 임시로 정해두고 `열린 질문`에 남겨서 나중에 다시 물어요.
- **⚠️ 표시**: 나중에 바꾸기 어려운 결정이에요. 한 번 더 확인해요.
- **중간 정리**: 질문 3~4개마다 지금까지 들은 걸 정리해 보여줘요. 틀린 데가 있으면 그때 말하면 돼요.
- **선택지에 없는 답**: 직접 써도 돼요. "다른 답" 칸에 자유롭게 적으세요.
- **모르는 말이 나오면**: "그게 무슨 뜻이에요?"라고 물으면 쉽게 다시 설명해 줘요.

### 중간에 멈추고 싶으면

그냥 멈춰도 돼요. 답은 받을 때마다 파일에 바로 적히니까, 다음에 `/pipeline:kickoff`를 치면 멈춘 곳부터 이어서 합니다.

### 앞에서 정한 걸 바꾸고 싶으면

"아까 정한 대여 기간을 7일로 바꿔줘"처럼 말하면 돼요. 다른 곳에 영향이 있으면(예: 화면 문구, 완료 조건) 같이 고칠지 물어요.

## 프로젝트 폴더에 남는 것

```
projects/<프로젝트>/            폴더 이름은 영어 (예: equipment-rental). Claude가 제안해요
├── spec.md                     기획서 (①에서 만들고 ②③⑤에서 고쳐요)
├── interviews/                 현장 인터뷰 질문지와 받은 답 (②)
│   └── 2026-11-03-관리자.md
├── stories.md                  기능 명세와 완료 조건 (④)
├── red-team.md                 빈틈 점검 기록 (⑤)
└── api.md                      API 명세 (개발 단계, 준비 중)
```

`spec.md` 맨 아래 **진행 상황** 체크리스트를 보면 어느 단계까지 끝났는지 알 수 있어요.

## 저장하고 올리기

단계가 끝날 때마다 Claude가 "커밋할까요?"라고 물어요. 커밋은 지금까지의 내용을 저장해 두는 거예요. 원하면 GitHub에 올리고 PR까지 만들어 줘요.

- **기획 레포**는 머지 제한이 없어요. 기획 담당이 GitHub에서 바로 머지해도 되고, Claude에게 맡겨도 됩니다.
- **프론트·서버 레포**는 개발자만 머지해요. Claude는 PR을 만드는 데까지만 해요.

## 자주 묻는 질문

**스킬 이름을 외워야 하나요?**
아니요. `/pipeline:kickoff` 하나면 됩니다. "기획 시작하자", "다음은 뭐 해?"처럼 말로 해도 맞는 스킬이 시작돼요.

**단계를 건너뛰어도 되나요?**
② 현장 인터뷰는 필요할 때만 하면 돼요. 나머지는 건너뛸 수는 있지만 권하지 않아요. 건너뛴 단계는 길잡이 지도에 표시돼서 나중에 돌아올 수 있어요.
